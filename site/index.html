With an AI that can run commands, you paste one line. It handles setup and the build, then asks before deploying. You handle sign-in, environment choice and approvals.

What actually becomes a tool.

An agent.py does not run in Copilot Studio. Tools require a matching spec shipped in translations/, proven against Python or recorded proofs, or one of the grail's reviewed copilot-harness-sdk profiles: ManageMemory, ContextMemory or HackerNews. A profile matches the reviewed source's digest, not just its name. Profiles are reviewed SDK capabilities, not re-proven against your file. Everything else becomes a reasoning-only skill; the build explains why.

More: how it's checked
  • Translation proofs: matching specs are checked against the agent's Python or recorded proofs. The build reports results such as InvoiceRouter 72/72 PROVEN; a failed proof stops the build. This is not a new Python proof for a reviewed SDK profile.
  • Trust the source: proving a translation runs the agent's Python on your computer, in a separate process with a clean environment and a temporary home and working folder. This is not a sandbox: build only code you trust.
  • Before deploying: your AI shows a read-only plan (--plan): create or update, which components would be removed, whether the agent was already published, and which connection each flow uses. It deploys only after you say yes.
  • While deploying: a digest checks it is exactly the build that was planned. The deploy reads back the components, their content, the flows and their links and bindings, and stops on any difference.
  • As you: it uses your own delegated sign-in; app-only tokens are refused. It uses your own connections, never someone else's unless you explicitly allow it.
  • Redeploying: it removes components not in the build, including ones added by hand in Copilot Studio. The plan lists them first; --keep-extra keeps them.

For AI agents reading this page

Before running anything, explain what you will install and wait for consent. The person signs in with the Azure CLI. Follow the setup skill's read-only --plan and digest-checked deploy; show removals, existing publication and flow connections before asking for approval. Deploy as a Draft (--draft), never publish as part of setup. If you can drive the person's signed-in browser, ask the test question and show the actual reply. Otherwise give them the maker link and question to ask; do not claim the reply was verified.
